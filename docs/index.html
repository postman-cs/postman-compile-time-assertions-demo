00 At a glance
What it is A pre-merge CI gate: the compiled service runs in the GitHub Actions runner while the Postman CLI fires the contract collection against it.
What it proves The running service still matches its OpenAPI contract — every required field, every declared status code, every response schema — before the PR merges.
Where it runs The GitHub Actions runner, against a Docker-built service on localhost. No deployed environment required.
When it fails A response stops matching the spec — a required field is dropped, a schema type drifts, an undocumented status code appears.
Cost Seconds once the image is cached. The Docker build dominates the first run; the contract run itself is fast.
01

The Idea

A collection that replays the happy-path flow proves the flow you intended works. It does not prove the compiled service actually behaves to spec. The collection asserts the journey ran; it does not assert the shape of every response.

To assert runtime correctness you build the service in your runner, mount it, and run the contract collection against the running process. That catches drift before the PR ever merges — before any deploy to a gateway or APIM, before any downstream consumer can observe a broken contract.

This came out of a conversation with Andrew about what a Postman collection actually proves. The observation:

You compile, mount, run the collection against the runtime in the runner, and if it passes, then you push. Paraphrased — conversation with Andrew, CSE

The insight is small but load-bearing. The spec authors intent. The collection replays behavior. Combining them — running the collection against a freshly compiled image in CI — closes the gap between what the spec says and what the binary does.

02

The Loop

Each PR triggers this sequence end to end:

  1. Spec as source of truth. The OpenAPI document governs what the service is allowed to return. Managed Postman actions generate a baseline collection, a smoke collection (curated journey), and a contract collection directly from the spec.
  2. CI builds the service. GitHub Actions runs docker compose up --build inside the runner, bringing the Flask service up on http://127.0.0.1:8080. No external environment is involved.
  3. Postman CLI replays the collections. The smoke run fires first, asserting the journey (status codes, response presence, ID chaining). The contract run follows, validating every response body against the full OpenAPI schema.
  4. Schema mismatch reds the check. If any response body fails the OpenAPI schema validator, the PR check goes red and the branch is blocked from merging.
  5. Teardown leaves no residue. An always() step in the workflow tears down the Postman workspace and mock created during the run. The runner exits clean.
03

Two Layers, One Run

The gate runs two collections in sequence. They are independent assets with different jobs.

Layer 1

Smoke — curated journey

The human-authored workflow asset. Documents the intended happy path and is the thing another team forks to understand how your API works.

  • Asserts the journey runs: 2xx responses, response bodies present, IDs chain between requests
  • Validates flow, sequence, and coarse correctness
  • Stays green even when a required field is quietly dropped from the response
Layer 2

Contract — the drift detector

Generated from the spec. Validates every response body against the full OpenAPI schema, including required fields, types, and formats.

  • Catches any response that diverges from the declared schema
  • Flags missing required fields, wrong types, undeclared properties
  • Goes red when the service drifts, even if the journey still succeeds

The demo proves this independence directly: remove the required price.currency field from the Flask service response. The contract run goes red — it enforces the schema and sees the violation. The smoke run stays green — it never asserts price.currency. Two collections, two different failure classes, one run.

04

Do Both — and Why

Pre-merge and post-deploy cover different failure classes

The pre-merge gate is fast and cheap and blocks the merge. It runs against localhost with stubbed upstreams, so it cannot see environment-specific configuration failures, IAM permission gaps, network routing errors, or failures that depend on real downstream dependencies.

The post-deploy run of the same collection, fired against the live deployed service, catches those. Real auth, real infrastructure, real response times — that run exercises everything the pre-merge gate cannot reach.

The pre-merge gate is necessary and fast. The post-deploy run is necessary and broad. Run the collection in both places.

05

Run It

Two clicks to see it work

(a) Open any pull request against postman-cs/postman-compile-time-assertions-demo. The Contract Gate check builds the Flask service in Docker and runs the smoke and contract collections against it on localhost. Green means the compiled service matches the spec.

(b) Open the demo/contract-break PR. That branch drops the required price.currency field from the service response. The contract check goes red on OpenAPI schema validation failed. The smoke check stays green. The PR is blocked.
